# Техническое задание на доработку бэкенда MemoLingvo: Игровой модуль

## 1. Общая информация
Настоящий документ описывает требования к серверной части приложения MemoLingvo для реализации игрового модуля, включающего две мини-игры («Словесная дуэль» и «Спринт-пары»), систему рангов и опыта, таблицу лидеров, а также возможность получения профиля бота для офлайн-соревнований.

**Базовый URL:** `http://dabilone123-001-site1.ltempurl.com/api`  
**Аутентификация:** Все эндпоинты, кроме авторизации, должны требовать валидный токен Firebase (передаётся в заголовке `Authorization: Bearer <firebase_id_token>`).  
**Идентификатор пользователя:** Внутренний `userID` (GUID), полученный при регистрации через `/Auth/register`. Связь с Firebase UID уже установлена в таблице `Users`.

---

## 2. Модели данных (серверная БД)

### 2.1 Таблица `GameSessions`
| Поле               | Тип данных     | Описание                                |
|--------------------|----------------|------------------------------------------|
| `sessionID`        | GUID (PK)      | Уникальный идентификатор игровой сессии |
| `userID`           | GUID (FK)      | Ссылка на `Users.userID`                 |
| `gameType`         | nvarchar(50)   | Тип игры: `word_duel` или `sprint_pairs` |
| `result`           | nvarchar(10)   | Исход: `win`, `lose`, `draw`             |
| `score`            | int            | Количество очков, набранных игроком      |
| `timeTakenSeconds` | int            | Затраченное время в секундах             |
| `accuracyPercent`  | int            | Процент точности (0–100)                 |
| `playedAt`         | datetime2(7)   | Время окончания игры (UTC)               |

**Индексы:** по `userID`, по `gameType`, по `playedAt`.

### 2.2 Дополнительные поля в таблице `Users`
| Поле          | Тип данных | Описание                           |
|---------------|------------|------------------------------------|
| `experience`  | int        | Общее количество очков опыта (XP)  |
| `rank`        | int        | Ранг пользователя (0 = Новичок, 1 = Любитель, 2 = Знаток, 3 = Мастер, 4 = Легенда) |

Ранг вычисляется по накопленному опыту согласно следующей шкале:
- 0–999 XP → `rank = 0` (Новичок)
- 1000–2999 XP → `rank = 1` (Любитель)
- 3000–5999 XP → `rank = 2` (Знаток)
- 6000–9999 XP → `rank = 3` (Мастер)
- ≥10000 XP → `rank = 4` (Легенда)

Очки опыта начисляются за каждую игру, формула расчёта опыта приведена в разделе 4.

## 3. API эндпоинты

### 3.1 Сохранение результата игры

**POST** `/Game/SubmitResult`

**Описание:** Клиент отправляет результат завершённой игры. Сервер сохраняет запись в `GameSessions`, обновляет опыт и ранг игрока в `Users`.

**Тело запроса (JSON):**
```json
{
  "userID": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "gameType": "word_duel",
  "result": "win",
  "score": 150,
  "timeTakenSeconds": 45,
  "accuracyPercent": 90
}
```

**Успешный ответ (200 OK):**
```json
{
  "message": "Game result saved",
  "newExperience": 5200,
  "newRank": 2,
  "rankName": "Знаток"
}
```

**Возможные ошибки:**
- 400 Bad Request – неверные параметры (например, `gameType` отличен от допустимых, `result` не `win/lose/draw`, отрицательные числа).
- 401 Unauthorized – отсутствует или неверный токен.
- 404 Not Found – пользователь с `userID` не существует.
- 500 Internal Server Error – ошибка базы данных.

**Логика обработки:**
1. Проверить существование пользователя по `userID`.
2. Вставить запись в `GameSessions`.
3. Рассчитать `experienceGain` по формуле (раздел 4).
4. Увеличить `experience` пользователя на `experienceGain`.
5. Пересчитать `rank` согласно шкале.
6. Сохранить изменения в `Users`.
7. Вернуть обновлённые значения.

### 3.2 Получение таблицы лидеров

**GET** `/Game/Leaderboard`

**Описание:** Возвращает список игроков, отсортированных по убыванию опыта. Предназначен для общего рейтинга.

**Параметры запроса:**
- `top` (необязательный, int, по умолчанию 20) – количество возвращаемых записей.

**Успешный ответ (200 OK):**
```json
[
  {
    "userID": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
    "email": "player1@test.com",
    "experience": 5200,
    "rank": 2,
    "rankName": "Знаток",
    "totalGames": 35,
    "wins": 20
  },
  ...
]
```

**Возможные ошибки:**
- 401 Unauthorized.
- 500 Internal Server Error.

**Логика:**
- Соединить таблицы `Users` и агрегированные данные из `GameSessions` (количество игр, побед).
- Отсортировать по `experience DESC`.
- Ограничить количество результатов параметром `top`.

### 3.3 Получение полной статистики пользователя

**GET** `/Game/UserStats/{userID}`

**Описание:** Детальная статистика конкретного игрока для отображения в профиле.

**Параметры пути:** `userID` – GUID пользователя.

**Успешный ответ (200 OK):**
```json
{
  "userID": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "email": "player1@test.com",
  "experience": 5200,
  "rank": 2,
  "rankName": "Знаток",
  "experienceToNextRank": 6000,
  "progressPercent": 73.3,
  "totalGames": 35,
  "wins": 20,
  "losses": 10,
  "draws": 5,
  "favoriteGame": "word_duel",
  "bestScore": 250,
  "averageAccuracy": 85.2,
  "totalTimePlayed": 1840
}
```

**Возможные ошибки:**
- 401 Unauthorized.
- 404 Not Found – пользователь не найден.
- 500 Internal Server Error.

**Логика:**
- Получить текущие `experience` и `rank` из `Users`.
- Вычислить `experienceToNextRank` и `progressPercent` на основе шкалы рангов.
- Из `GameSessions` агрегировать: количество игр (`COUNT`), побед (`result = 'win'`), поражений, ничьих, любимый тип игры (по количеству), максимальный счёт, среднюю точность, суммарное время.

### 3.4 Получение профиля «бота» (для офлайн-игры)

**GET** `/Game/BotProfile/{userID}`

**Описание:** Возвращает усреднённые показатели игрока, которые клиент использует для имитации поведения бота в офлайн-матчах. Позволяет подстраивать сложность под реального соперника.

**Успешный ответ (200 OK):**
```json
{
  "averageSpeed": 4.5,
  "accuracy": 82
}
```
- `averageSpeed` – среднее время (в секундах), за которое игрок решает одно задание (например, находит пару или составляет слово). Рассчитывается как общее время игры, делённое на количество выполненных заданий (или просто среднее по последним N играм).
- `accuracy` – средний процент точности по всем играм.

Если у пользователя ещё нет игр, вернуть значения по умолчанию (например, `averageSpeed: 6.0`, `accuracy: 70`).

**Возможные ошибки:**
- 401 Unauthorized.
- 404 Not Found – пользователь не существует.
- 500 Internal Server Error.

**Логика:**
- Из `GameSessions` по `userID` взять последние 10–20 записей (для актуальности).
- Рассчитать `averageSpeed` как среднее от `timeTakenSeconds / (score / базовые_очки_за_задание)` или просто общее время / количество игр. Допустимо упрощение: среднее `timeTakenSeconds` по играм, делённое на среднее количество действий (можно принять за средний score/50).
- `accuracy` = среднее арифметическое `accuracyPercent`.
- Если записей нет, вернуть дефолтные значения.

## 4. Начисление очков опыта (XP)

За каждую игру игрок получает опыт, вычисляемый по формуле:

```
XP = baseXP + bonusXP
```

### 4.1 Базовая часть (baseXP)
Зависит от типа игры и исхода:

| Тип игры      | Победа | Поражение | Ничья |
|---------------|--------|-----------|-------|
| word_duel     | 100    | 20        | 50    |
| sprint_pairs  | 100    | 20        | 50    |

### 4.2 Бонусная часть (bonusXP)
Зависит от качества игры, чтобы поощрять быстрые и точные решения:

```
bonusXP = (score * accuracyPercent / 100) * speedMultiplier
```

- `score` – очки, набранные игроком (из запроса).
- `accuracyPercent` – точность в процентах (0–100).
- `speedMultiplier` – коэффициент скорости:
  - Если `timeTakenSeconds < 30` → 1.5
  - Если `30 ≤ timeTakenSeconds < 60` → 1.2
  - Если `60 ≤ timeTakenSeconds < 120` → 1.0
  - Иначе → 0.8

**Пример:**
Победа в word_duel, score=200, accuracy=90%, time=25с → XP = 100 + (200 * 90/100 * 1.5) = 100 + 270 = 370

**Ограничения:**
- Максимальный XP за одну игру — 500 (чтобы не было слишком быстрого роста).
- Если результат – поражение, бонусная часть не начисляется (bonusXP = 0).

## 5. Требования к реализации

- **База данных:** Рекомендуется использовать реляционную СУБД (SQL Server, как предполагается из контекста ASP.NET).
- **ORM:** Entity Framework Core (Code-First миграции).
- **Аутентификация:** Проверять Firebase ID Token на каждом запросе, извлекать `uid`, сопоставлять с `Users.userID` (или использовать кастомный middleware, если ещё не реализовано). Эндпоинты `/Game/*` должны быть защищены атрибутом `[Authorize]`.
- **Валидация:** Использовать Data Annotations или FluentValidation для входных моделей.
- **Логирование:** Все действия с играми должны логироваться (сохранение сессии, обновление опыта).
- **Транзакции:** При сохранении сессии и обновлении опыта использовать транзакцию для обеспечения согласованности.
- **Swagger:** Обновить документацию Swagger для новых эндпоинтов.

## 6. Дополнительные замечания

1. **Балансировка подбора соперников:** В будущем планируется многопользовательский режим реального времени. Пока подбор не требуется, но сервер должен хранить достаточно данных, чтобы можно было ввести matchmaking по `rank` или `experience`.
2. **Заглушка для `BotProfile`:** Клиент пока использует захардкоженные значения, но эндпоинт должен быть готов к возврату реальных данных.
3. **Совместимость с существующими эндпоинтами:** Новые таблицы и методы не должны ломать текущую синхронизацию колод и карточек.
4. **Коды ошибок:** Все ответы должны иметь единообразную структуру ошибок (например, `{ "error": "message" }`).
